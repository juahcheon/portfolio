# 공고를 고르고 회사별 글을 쓰는 법

## 1. 공고는 제목보다 제출 조건을 먼저 본다

채용 정보는 실행 당일의 사람인 공고와 회사 공식 채용 페이지를 직접 확인한다. 검색 결과의 요약·추천 태그·AI 적합도만으로 판단하지 않는다. 이미지 공고는 확대·스크롤해서 읽고, 다른 사이트로 연결되면 그곳의 지원 양식도 확인한다.

회사마다 다음을 짧게 기록한다.

| 확인할 것 | 판단 기준 |
|---|---|
| 회사·직무·공고 식별자 | 같은 회사의 다른 직무를 섞지 않고 기존 지원과 대조 |
| 마감 일시 | 날짜뿐 아니라 시간, 채용 시 마감·조기 종료 확인 |
| 담당 업무 | 실제 프론트엔드 비중, 제품·관리자 화면·유지보수·파견 업무 구분 |
| 필수·우대 기술 | 필수 경력과 우대 경력 구분. 공고 안의 신입/경력 모집 단위별로 읽기 |
| 고용 조건 | 정규직·계약직·인턴, 계약기간·전환 조건·수습 조건 |
| 근무지 | 본사 주소와 실제 근무지 구분. 출퇴근 시간은 확인된 출발지 기준 |
| 회사 규모 | 인원·기준연도 등 확인 가능한 사실. 매출만으로 개발 조직이 크다고 단정하지 않기 |
| 지원 방식 | 사람인 즉시지원, 외부 사이트, 지정 이력서·자기소개서 문항·별도 파일 |
| 추가 요구 | 경력·졸업·성적증명서, 사진, 포트폴리오, 자격·어학, 계열사 중복지원 제한 |

마감 임박 공고 중 적합한 곳을 먼저 고른다. 최소 경력 2년까지 지원 가능하다는 합의는 경력을 2년으로 기입하라는 뜻이 아니다. 공고가 신입도 받으면 실제 경력을 유지하고 신입 전형으로 지원할 수 있다. “3년 우대”와 “3년 이상 필수”는 다르게 판단한다.

희망 지역 밖이거나 규모가 작아도 기술·업무·조건이 좋으면 근거와 차이를 알려 검토한다. 확인되지 않은 연봉·문화·사업 전망은 장점으로 만들어 쓰지 않는다. 예상치 못한 계약·인턴 조건은 조용히 수용하지 말고 사용자 판단을 받는다.

## 2. 예외를 발견했을 때

| 상황 | 다음 행동 |
|---|---|
| 별도 자기소개서 파일 또는 지정 양식 | 실제 양식·문항·분량·파일 형식을 읽고 사용자에게 알려 처리 방침 확인. 이미 해당 작성·제출을 승인했다면 계속 진행 |
| 증명서가 필수인데 없음 | 없어도 된다고 가정하거나 임의 파일로 대체하지 않기. 사용자에게 대안 선택을 묻고 해당 회사만 보류 |
| 사용자가 “지원하지 말고 다른 곳” | 보류/제외 사유를 남기고 새로운 후보로 교체. 보류 회사를 완료 수에 넣지 않기 |
| 기존 이력서로 답할 수 있는 문항 | 사실 범위에서 직접 작성. 이미 승인된 작성 작업에 재승인 요구하지 않기 |
| 연봉·입사일·병역 등 확인 안 된 필수 항목 | 최신 대화·자료를 먼저 확인하고 없으면 질문. 임의 기본값 입력 금지 |
| 인증·로그인 필요 | 현재 도구 정책을 따르고 필요한 사용자 조작만 요청. 다른 후보 조사·초안은 계속 |
| 이미 지원한 공고 | 중복 제외. 재지원 의도나 재공고 여부가 불명확하면 상태 확인 |

예전에 서류 때문에 포기한 회사는 그 **공고의 조건**과 함께 기록한다. 회사 이름 자체를 영구 금지 목록으로 만들지 않는다.

## 3. 원고를 만들기 전에 연결표를 만든다

각 회사의 실제 요구 2~3개를 골라 검증된 경험과 연결한다. 아래는 이 포트폴리오에서 찾아볼 소재이며, 다른 지원자의 경험으로 복사하지 않는다. 정확한 역할·반영 상태는 [경험 조사](evidence-and-documents.md)에서 다시 확인한다.

| 공고의 관심사 | 우선 검토할 경험 | 설명할 핵심 |
|---|---|---|
| 제품 프론트엔드·UX | 이미지 스튜디오, 공공자료 화면, 생성 상태 복구 | 사용자가 어디에서 막혔고 화면·상태 흐름을 어떻게 바꿨는지 |
| 관리자·B2B·대시보드 | Ops 요청 주기·오류 표시·상태 분리 | 느린 응답, 마지막 정상 데이터, 중복 요청과 화면 이동 처리 |
| UI 일관성·유지보수 | 스타일 역할 분리, 색·글꼴·간격 토큰 | 화면마다 달랐던 기준을 어떻게 코드로 정리했는지 |
| AI 서비스·개발 생산성 | Docs 표준화, 업데이트 작성 스킬 | 입력 근거·작성 규칙·검증·동료 사용 방법까지 다뤘는지 |
| 웹·풀스택 | API 계약·검증·페이지네이션, 교육 사이트 링크 입력 | 직접 수정한 범위와 백엔드 개발자와 협의한 범위를 구분 |
| Next.js·서비스 출시 | 이전 직장의 Baro, 확인된 사이트 전환·배포 경험 | 화면 설계·구현·API 연동·배포 중 본인 책임 범위 |

같은 소재를 여러 회사에 써도 괜찮다. 회사 이름만 치환한 지원동기는 피하고, 그 회사의 업무에서 해당 경험이 왜 필요한지 연결한다. 필요 없는 기술 이름을 나열하지 않는다.

## 4. 사람이 면접에서 설명할 수 있는 문장으로 쓴다

기존 사람인 자기소개서 항목을 유지하되, 회사가 별도 문항을 지정했다면 그 질문에 답한다. 기존 4항목은 보통 지원동기, 실무 강점, 문제 해결, 협업·학습으로 운영했다. 숫자 4에 맞추기 위해 지정 문항을 합치거나 빼지 않는다.

- 최근 실무를 중심으로 `어떤 문제 → 내가 한 판단·행동 → 확인된 변화`를 쓴다. 결론은 근거 범위까지만 말한다.
- “일이 없으면 일을 요청한다”는 성향은 개선할 부분을 찾아 제안하고 개발팀과 협의한 실제 행동으로 보여 준다. 회사 동료의 역량을 낮춰 자신을 높이지 않는다.
- 상사에게 화면 개선을 좋게 평가받았다는 이야기는 평가로 쓴다. 추후 디자인을 맡기자는 말은 완료된 프로젝트 실적이 아니다.
- “AI로 백엔드도 할 수 있다”는 자신감은 도구 사용과 API 이해, 직접 작성·검토·검증한 범위로 풀어 쓴다. 백엔드 전체 설계 경력으로 확대하지 않는다.
- 재직 중이면 재직 중이라고 쓴다. 퇴사 예정일은 예정이며, 과거 퇴사한 것처럼 바꾸지 않는다. 사이트의 월 단위 경력 합산이 바뀌어도 실제 날짜를 임의 수정하지 않는다.
- “혁신을 선도”, “무한한 성장”, “탁월한 시너지”, “완벽한 사용자 경험” 같은 추상적 자기평가를 줄이고 실제 행동을 쓴다. 모든 문단을 “이를 통해 역량을 키웠습니다”로 끝내지 않는다.
- 제목은 핵심 경험과 지원 직무를 구체적으로 표현한다. 과장된 수식어보다 “화면 설계부터 API 연동까지”처럼 책임 범위가 드러나는 제목을 쓴다.

예를 들어 “대규모 트래픽을 최적화했습니다”는 측정·운영 근거가 없으면 쓸 수 없다. “이전 조회가 끝난 뒤 다음 조회를 예약하도록 바꾸고, 실패 시 마지막 정상 데이터와 갱신 시각을 보여 주었습니다”는 실제 변경이 확인됐다면 쓸 수 있다.

## 5. 붙여넣기 전·후 모두 검수한다

1. 회사명·직무·회사 정보·기술 요구가 현재 공고와 맞는지 읽는다.
2. 각 주장에 본인 경험 근거가 있는지 확인한다. 매출·사용량·개선율을 창작하지 않는다.
3. 소리 내 읽듯 읽고 긴 문장, 같은 어미·접속사 반복, AI식 추상어를 다듬는다.
4. 입력 원고에 `\t`, `\n\n`, 공백만 있는 줄이 없는지 검사한다. 문단 사이는 `\n` 한 번이다. 여기서 말한 “탭 두 번”을 탭 문자만의 문제로 오해하지 않는다.
5. 웹 편집기의 빈 `<p>`, `<br>` 중복, 공백 문자만 있는 문단도 화면에서 확인한다. 소스 문자열만 깨끗하다고 끝내지 않는다. PDF·포트폴리오의 기존 디자인 간격은 이 규칙 때문에 바꾸지 않는다.
6. 저장 후 다시 읽은 본문까지 확인하고, 제출 뒤 실제 제출본과 다시 대조한다.
