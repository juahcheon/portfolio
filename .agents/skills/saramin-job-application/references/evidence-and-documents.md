# 경험을 조사하고 포트폴리오·PDF에 반영하는 법

## 사실을 확정하는 순서

최신 사용자 설명, 현재 포트폴리오·이력서, 본인 커밋·PR·코드, 당시 테스트·배포 기록을 함께 본다. 서로 다르면 단정하지 말고 차이를 확인한다. 사용자에게는 코드로 확인할 수 없는 **동기·판단·협업 과정·실제 반영 여부**를 하나씩 묻는다. 먼저 찾을 수 있는 사실을 사용자에게 다시 조사시키지 않는다.

사용자가 최근 인턴 경험으로 내용을 바꾸자고 했다면 예전 개인 프로젝트 중심 자기소개서를 그대로 유지하지 않는다. 그렇다고 이전 경력을 모두 삭제하지도 않는다. 실제 프론트엔드 업무와 연결되는 강한 사례를 우선한다.

## 커밋을 “꼼꼼히 봤다”는 말의 기준

1. 접근 가능한 저장소와 작성자 이름·메일 별칭, 브랜치를 확인한다. 계정명이 같다는 이유만으로 모든 변경을 본인 작업으로 간주하지 않는다.
2. 이 포트폴리오에서는 AI Switch, AI Switch Docs, AI Switch Ops, gongong-ai-edu를 우선 확인했다. 로컬 이름과 원격 이름이 다를 수 있다. 당시 AI Switch는 `nuri-ai`, 현재 Docs는 `ai-switch-web`, 초기 Docs는 `ai-switch-docs`였다. 추가 참여 저장소도 찾되 접근 권한을 가정하지 않는다.
3. 요청된 기간·범위의 본인 커밋과 PR 목록을 만든다. 커밋 제목만 읽고 끝내지 말고 변경 파일·diff·관련 코드·테스트를 읽는다. 중요한 사례는 호출 흐름과 에러·복구 경로까지 추적한다.
4. squash·merge·동일 패치 중복, 타인 커밋 혼입, revert, 초안·미병합 PR을 구분한다. 커밋 수 자체를 성과로 쓰지 않는다.
5. “코드를 작성함”, “PR을 올림”, “병합됨”, “운영 반영됨”, “효과를 측정함”을 별도로 기록한다. 공개한 문장은 확인된 단계까지만 말한다.
6. 어떤 저장소·기간·변경을 확인했고 무엇이 누락됐는지 남긴다. 접근 실패나 바이너리·생성 파일까지 모두 검토했다고 포장하지 않는다. 기존 근거가 충분하면 변경분만 재확인한다.

경험 하나는 다음 항목으로 남기면 다른 회사에 재사용하기 쉽다.

```text
사례 ID / 저장소 / 기준일 / 본인 역할
문제 / 판단 이유 / 실제 변경 / 확인 결과
관련 커밋·PR·파일 / 당시 테스트와 이번 확인의 구분
병합·배포 상태 / 수치의 측정 조건 / 과장하면 안 되는 경계
잘 맞는 직무 / 면접에서 설명할 질문
```

비공개 회사 코드·운영 주소·스크린샷은 비공개 근거에만 둔다. 공개 포트폴리오에는 허용된 화면과 일반화한 문제 해결 과정만 쓴다. 테스트 로그에 기록된 과거 실행을 이번에 실행한 테스트처럼 보고하지 않는다.

## 이 작업에서 특히 조심했던 해석

| 소재 | 근거가 확인됐을 때 쓸 수 있는 설명 | 넘어가면 안 되는 주장 |
|---|---|---|
| 이미지 스튜디오 | 복잡한 화면 분할·입력 흐름을 정리하고 프롬프트 예시·결과 활용 흐름 개선 | 측정하지 않은 전환율·이탈률 개선 |
| 공공자료 화면 | 사용자가 자료·출처를 찾고 질문을 이어가는 흐름 개선 | 확인하지 않은 실제 사용자 증가 |
| 디자인 토큰 | 색·글꼴·간격 기준을 정리하고 스타일을 역할별로 분리 | “CSS 4만 줄”, 분리만으로 네트워크 트래픽 절감 단정 |
| Ops 조회 | 이전 요청 완료 후 다음 요청 예약, 조회 분리, 정상 데이터·갱신 시각 유지, 오류와 빈 결과 구분 | 서버 전체 성능 개선이나 비용 절감으로 확대 |
| 번들 감소 | 같은 Node·의존성 등 조건을 맞춘 전후 빌드의 초기 JS 크기 비교 | 번들 감소율을 응답 속도·매출·트래픽 감소율로 바꾸기 |
| Docs 표준화 | 확인된 Astro·Starlight 문서 구조와 팀 활용 방식 | 팀 전체 문서를 혼자 처음부터 모두 만들었다는 표현 |
| 업데이트 스킬 | GitHub 변경 이력을 읽고 월별 원고를 작성하도록 규칙·검증·사용 가이드 구성 | 자동 예약 발행, 무검수 운영, 업데이트 내용을 사람이 매번 정리해 줘야만 동작한다고 설명 |
| 자발적 개선 | 먼저 문제를 찾아 제안하고 개발팀 동의 후 진행한 일 | 요청을 받아 만든 업데이트 스킬까지 모두 자발적이라고 묶기 |
| 교육 사이트·API | 본인이 작성한 프론트엔드·API 검증·저장 처리와 확인된 반영 상태 | 열려 있는 PR을 이미 운영 중인 성과로 설명 |
| 디자인 평가 | 상사·동료가 화면 개선을 좋게 평가했다는 사용자 설명 | 나중에 맡기자는 프로젝트를 완료한 실적으로 추가 |

이 표는 문장을 그대로 복사하는 경험 증명서가 아니다. 수치·PR 상태·재직 기간은 현재 근거에서 다시 가져온다. 사용자가 예전에 과장을 제안했더라도 “거짓은 작성하지 않는다”는 최종 기준을 따른다.

## 포트폴리오 → PDF → 사람인

내용 전체를 고치는 요청에만 이 순서를 적용한다. 일일 회사 지원에서는 이미 정리된 경험을 활용해 자기소개서만 맞춘다.

1. **원본 확인:** 실제 배포 데이터와 PDF 생성 소스를 찾는다. 이 저장소는 `web/data/portfolio.json`과 레거시 경로가 함께 언급되어 왔다. `AGENTS.md`·콘텐츠 문서·실제 로더를 확인해 원본/동기화 방향을 정하고 오래된 파일만 고치지 않는다.
2. **포트폴리오 초안:** 실무 중심 소개·트러블슈팅을 수정하고 전후 문장을 검토할 수 있게 한다. UI·색·레이아웃·타이포를 임의로 바꾸지 않는다. 사용자가 최종본을 정하겠다고 했다면 그 확인을 기다린다.
3. **PDF 반영:** 확정 문구를 기존 이력서 PDF 전용 소스에 반영한다. 기존 디자인·사진·프로젝트 이미지를 보존한다. AI Switch의 공개 가능한 화면도 빠뜨리지 않는다. 내부 Ops 화면을 대신 넣지 않는다.
4. **출력 검증:** 기존 생성 절차로 실제 PDF 파일을 만든다. 파일명·수정 시각·크기·가능하면 해시를 확인하고 페이지를 렌더링해 잘림·빈 페이지·한글·이미지·링크를 검수한다. HTML 원본만 저장하고 PDF를 만들었다고 하지 않는다. 추가 패키지가 필요하면 기존 런타임·도구부터 찾는다.
5. **사람인 반영:** 확정 문구를 저장하고 다시 읽어 확인한다. 첨부 PDF 교체가 요청됐다면 새 파일 업로드 성공과 올바른 파일 선택을 확인한 뒤 기존 첨부를 정리한다. 유일한 기존 파일부터 지우지 않는다.
6. **기록:** 어느 버전이 언제부터 제출됐는지 남긴다. 과거 지원에 보낸 PDF와 원고를 새 내용으로 덮어쓰지 않는다.

기존 이력서 제목이 “웹 개발자”라면 일일 지원 때 무조건 “프론트엔드 개발자”로 되돌리지 않는다. 포트폴리오·PDF의 주요 사례는 프론트엔드 채용에 강한 순서로 구성하고, 회사별 자기소개서에서 웹·API 경험의 비중을 조절한다.

## 저장소 변경을 함께 요청받은 경우

최신 저장소 지침과 사용자의 실제 commit/push/PR/merge 요청 범위를 따른다. 기존 승인은 같은 범위에서 재사용한다. 작업 중인 다른 변경을 섞지 않고 파일별로 stage한다. 개인 지원서·인증번호·비공개 회사 자료를 공유 스킬과 함께 올리지 않는다. dirty 상태를 정리하려고 임의 reset·stash·강제 push를 하지 않는다. 변경한 종류에 맞게 검증하고 완료·미완료를 구분한다.
