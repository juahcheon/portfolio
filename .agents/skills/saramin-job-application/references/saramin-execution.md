# 사람인에서 저장·지원·검증하는 순서

## 브라우저 연결부터 확인한다

현재 환경의 브라우저 도구·관련 스킬 설명을 먼저 읽고 그 API만 사용한다. 특정 MCP 이름, 탭 번호, 이력서 번호, CSS 선택자, 버튼 위치를 재사용하지 않는다. 기존 Chrome을 요청했다면 연결된 Chrome과 실제 열린 사람인 탭부터 확인한다. 이력이 없는 새 브라우저를 임의로 로그인된 환경처럼 취급하지 않는다.

계정이 맞는지 확인하고 로그아웃 상태라면 로그인 화면을 열 수 있는 범위까지 연 뒤 사용자에게 필요한 조작만 알린다. 새 환경의 브라우저 연결·로그인 상태·파일 권한은 저장소 clone으로 전달되지 않는다. 접근 불가 원인을 구분해 말하고 공고 조사·원고 준비를 계속한다.

인증번호·비밀번호·쿠키는 공유 파일이나 작업 기록에 남기지 않는다. 현재 도구가 허용하는 인증 방법을 따른다. 보안 정책으로 막힌 파일·페이지 접근을 로컬 서버나 다른 프로토콜로 우회하지 않는다. 도구가 허용하는 파일 업로드·아티팩트 미리보기 경로를 사용하고, 그 경로도 없으면 필요한 사용자 조작을 정확히 요청한다.

## 제출 전 준비

1. 사람인과 이미 사용한 외부 채용사이트의 지원 내역을 확인해 중복을 제외한다. 지원한 회사 이름뿐 아니라 공고·직무·접수 번호를 확인한다.
2. 회사별 공고 조건·필수 서류·원고·첨부 목록을 검토 가능한 HTML 또는 기존 검토 문서로 준비한다. 승인 때문에 초안 작성을 미루지 않는다.
3. 원래 선택한 사람인 이력서, PDF 파일명·버전, 포트폴리오 URL을 기록한다. 이 작업에서는 포트폴리오 링크 4개와 PDF를 함께 전달해 왔지만, 새 환경에서는 **현재 실제 목록**을 읽는다. 개수나 링크를 기억으로 채우지 않는다.
4. 불필요한 정보 공개 설정·취업 제안 수신·마케팅 동의는 바꾸지 않는다. 필수 지원 동의와 선택 광고를 구분한다. 지원 후 추천되는 다른 회사까지 일괄 지원하지 않는다.
5. 새 승인이 필요한지 현재 사용자 지시와 도구 정책으로 판단한다. 필요하다면 회사명·직무·고용 조건과 전달되는 연락처·주소·학력·경력·자기소개서·첨부의 범위를 설명하고 승인받는다. 여러 회사의 준비가 끝났으면 한 번에 물을 수 있다. 승인된 범위가 바뀌지 않았다면 매번 다시 묻지 않는다.

## 가장 중요한 규칙: 회사별 처리를 끝낸 뒤 다음 회사로 간다

### A. 해당 회사 글 저장

- 현재 이력서의 자기소개서 항목만 회사별 원고로 바꾼다. 경력·학력·연락처·PDF를 불필요하게 다시 입력하지 않는다.
- 항목 제목과 본문을 모두 입력하고 사이트가 요구하는 항목 저장과 최종 `작성완료`를 구분한다. 실제 버튼 이름은 현재 화면을 읽는다.
- 저장 성공 표시를 확인한 뒤 다시 열어 읽는다. 글자 수·본문이 이전 값이면 화면 반영과 저장 상태를 확인한다. 필요 시 포커스를 이동해 입력 이벤트를 반영하되 무작정 저장 버튼을 반복 누르지 않는다.
- 빈 문단·중복 줄바꿈과 회사명이 다른 곳에 남았는지 눈으로 확인한다. 현재 저장된 자기소개서가 어느 회사용인지 비공개 기록에 남긴다.

### B. 새로운 지원 화면에서 확인

- 이전에 열어 둔 지원 모달은 닫고, 그 회사 공고에서 새로 지원 화면을 연다. 오래된 창이 최신 이력서를 반영했다고 가정하지 않는다.
- **회사·직무 → 선택 이력서 → 자기소개서 제목·본문 → PDF·포트폴리오 → 신입/경력 등 지원 구분** 순으로 확인한다.
- 지원 화면에서 본문을 볼 수 없다면 저장된 이력서를 먼저 확인하고, 제출 뒤 제출본 검증이 필요한 상태임을 기록한다.
- 신입 전형으로 지원해도 기존 경력은 유지한다. 필수 서류가 갑자기 나오면 해당 회사만 보류하고 사용자에게 묻는다.

### C. 제출하고 상태 확인

- 필요한 승인이 충족됐으면 최종 제출한다. 클릭 직후 완료 메시지·접수 번호·지원 내역을 확인한다.
- 시간 초과나 브라우저 오류가 나면 새 지원 내역 또는 확인 가능한 접수 결과를 먼저 읽는다. 제출 버튼을 다시 누르기 전에 **이미 접수됐는지** 해결한다.
- 접수 여부가 확인되지 않으면 `결과 미확인`으로 남긴다. 새 회사 준비는 계속할 수 있지만 같은 공고를 자동 재제출하지 않는다. 제출 내용 보존 방식도 불명확하다면 공용 이력서 변경 전에 확인한다.

### D. 실제 제출본 대조

지원 내역에서 해당 건의 **제출 이력서 보기·인쇄본** 등 실제 사본을 연다. 편집 중인 원본 이력서를 제출 사본으로 착각하지 않는다.

| 검증 항목 | 확인 내용 |
|---|---|
| 접수 대상 | 회사·공고·직무·지원 시각·접수 번호 |
| 자기소개서 | 회사별 원고와 모든 항목의 제목·본문 일치 |
| 사실 정보 | 의도하지 않은 경력·학력·지원 구분 변경 없음 |
| 첨부 | 선택한 PDF 버전과 포트폴리오 URL 목록 일치 |
| 증거 | 확인 가능한 제출본 URL·텍스트 또는 필요한 화면 기록 |

CRLF/LF와 NBSP 같은 표시 차이는 구분해서 비교한다. 모든 공백을 지우고 비교하면 빈 문단과 줄바꿈 오류를 놓친다. 제출본을 JSON으로 추출했다면 [검사기](../scripts/check_application_records.py)의 `--submitted`로 대조한다. 실제 사본에서 읽은 값을 사용하며 기대 원고를 복사해 검증값으로 만들지 않는다.

사이트가 제출 이후에도 공용 이력서 변경을 지원 건에 반영하는 구조인지 확인한다. 이 작업에서 사람인 제출 사본을 대조했던 방식을 따르되, 새 외부 사이트도 같다고 가정하지 않는다. 불명확하면 지원 건별 사본 또는 별도 이력서가 가능한지 확인한 뒤 다음 회사 글을 저장한다.

일치가 확인된 뒤에만 `검증 완료`로 기록하고 다음 회사로 간다. 불일치가 있으면 수정을 지원 사이트에서 허용하는지 확인하고 사용자에게 알린다. 임의로 취소·재지원하거나 조용히 성공 처리하지 않는다.

## 외부 채용사이트와 예외

Greeting·Ninehire·회사 자체 채용 페이지 등으로 넘어가면 해당 사이트의 필수 항목과 제출 조건을 새로 읽는다. 사람인 이력서가 자동 전달된다고 생각하지 않는다. 이미 사용자에게 받은 영문 이름·사진·주소 등은 최신 자료에서 재사용하고, 없는 필수 정보만 묻는다.

사용자가 지정 양식의 자기소개서 작성까지 맡겼다면 실제 경험으로 문항별 답변을 작성한다. 파일이 필요하면 지정 형식·분량대로 만들고 열어 확인한다. 그 승인이 성적증명서·경력증명서 같은 증빙 문서의 생성을 허용하는 것은 아니다.

UI가 달라지면 최신 화면을 다시 읽고 절차를 조정한다. 예전 버튼 위치·서버 경로를 외워 강행하지 않는다. 오류가 반복되면 확인된 상태를 기록하고, 안전하게 확인할 수 있는 다른 화면이나 사용자 조작으로 해결한다.

## 끝내기

목표 수는 **이번 요청으로 새로 접수된 건**으로 센다. 후보·검토본·제외·중복·접수 미확인을 섞지 않는다. 접수 확인과 원고 검증이 서로 다른 단계라면 그 차이까지 보고한다.

기존 HTML에 회사 정보와 실제 지원 내용을 추가하고 확인 가능한 링크를 제공한다. 현재 기본 이력서에 마지막 회사 글이 남아 있음을 기록한다. 일반 소개로 되돌리기는 사용자가 원하거나 기존 운영 방침이 있을 때만 한다. 로그인·승인 대기 중인 탭이나 사용자가 보고 있는 탭을 임의로 닫지 않는다.
